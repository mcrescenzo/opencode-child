# opencode-child

`opencode-child` is a local opencode plugin for starting and inspecting disposable child `opencode serve` processes from a parent opencode session.

## Install

For a local clone or copied checkout, register `opencode-child.js` in your
`opencode.json` under the singular `"plugin"` key by an absolute path or a
path relative to the `opencode.json` file that declares it:

```json
{
  "plugin": ["/path/to/opencode-child/opencode-child.js"]
}
```

For the published npm package, install it where opencode resolves plugins
and register the package name instead:

```json
{
  "plugin": ["@mcrescenzo/opencode-child"]
}
```

Restart opencode after changing plugin config. Running sessions keep the already-loaded plugin set.

## Prerequisites

- The `opencode` binary must be on `PATH` — this plugin spawns `opencode serve` child processes. `OPENCODE_BIN` is supported as a custom-binary override, but safe mode treats it like `opencodeBin` and rejects it unless explicitly unsafe-approved.
- Node.js `>=20.11.0` (the plugin's package `engines.node` floor; use a runtime compatible with opencode as well).
- Supported opencode route contract: verified against opencode `1.17.13`; startup fails closed if a child server lacks required startup routes. Optional inspection routes degrade into capability flags.

## Package Manager

npm is canonical for this package. Use the tracked `package-lock.json` with `npm install`, `npm ci`, `npm test`, `npm run smoke`, and `npm pack --dry-run --json`.

One transitive optional dependency, `msgpackr-extract`, declares an install script through `node-gyp-build-optional-packages`. It is optional native acceleration from the opencode dependency graph; release and CI dependency checks should use npm's lockfile and may use `--ignore-scripts` when only dependency resolution is being verified.

## Hooks

The plugin registers three opencode hooks:

- `tool`: registers the `oc_*` tools listed below.
- `event`: forwards parent session events to per-child notification managers so `oc_prompt` can queue best-effort completion notifications.
- `dispose`: stops live plugin-managed children and aborts their SSE event readers, then clears registry/notification caches, when the plugin unloads.

## Tools

- `oc_child_start`: start a child server on `127.0.0.1` with a random port and generated HTTP Basic auth by default.
- `oc_child_status`: inspect health, process state, sessions, registries, trust posture, and logs.
- `oc_child_stop`: stop by advisory `/instance/dispose`, then PID/process-group verification and termination for live plugin-managed children. `childId: "all"` requires `confirmAll: true`.
- `oc_child_restart`: restart using the saved child spec and refreshed startup inspection.
- `oc_session_create`: create a child session.
- `oc_prompt`: send a prompt with bounded async polling; returns partial inspection on timeout and watches the child session for best-effort parent notifications.
- `oc_inspect`: aggregate child/session messages, diffs, todos, registries, and logs.
- `oc_events`: return bounded best-effort SSE event history.
- `oc_command`, `oc_shell`, `oc_permission`: bounded wrappers for verified server endpoints.
- `oc_plugin_smoke_test`: start, inspect, create a session, stop, and return evidence.

## Trust Modes

- `inherit` is the default. It may inherit normal project/config/env/MCP behavior, but child XDG data/cache/state are isolated by default, so auth-file provider state is not inherited unless `inheritData: true` is explicitly approved.
- `safe` is best-effort local isolation: loopback by default, `--pure`, child config dir, isolated XDG data/cache/state, generated Basic auth, token-like env stripping, and conservative generated permissions. Non-loopback safe-mode starts remain a high-risk request, but the plugin refuses plaintext HTTP child connections until a TLS-backed path exists. Safe mode is not a security sandbox.
- `full-trust` is explicit, parent-approved, and required for `dangerouslySkipPermissions`.

## Safety Defaults

- Child servers bind only to loopback by default. Non-loopback hostnames are reported as high-risk and still mention `allowNonLoopback: true` for compatibility with existing approval metadata, but spawned child connections are refused because opencode child Basic auth would otherwise travel over plaintext HTTP. Use loopback until a TLS/proxy connection path is supported.
- Child server passwords are generated by default and redacted from tool output and metadata. The private registry stores enough auth material for lifecycle recovery.
- Public tool results, including `oc_inspect`, bound both visible output and structured metadata. High-volume strings are truncated and large arrays/objects are summarized so logs, events, transcripts, and diffs do not expand unbounded in parent tool-result storage.
- Caller-supplied `configDir`, `dataDir`, `cacheDir`, or `xdgStateDir` are rejected by default because `configDir` writes an `opencode.json` file. They require `allowExternalDirs: true` and parent approval.
- Safe mode rejects permissive permissions, MCP config, remote/npm plugin specs, token-like env overrides, full env inheritance, and custom `opencodeBin`/`OPENCODE_BIN` unless explicitly unsafe-approved.
- `inheritGlobalConfig: false` and `inheritMcp: false` are only honored in safe mode (`trustMode: "safe"`, the `--pure` child). They are rejected for `inherit` and `full-trust` (which inherit global config/MCP by design); omit the flags for those modes.
- The default registry moved from project `.opencode/opencode-child` to a user-private XDG state directory namespaced by project path. Set `OPENCODE_CHILD_STATE_DIR` only for explicit fixture/debug use.
- Private state uses restrictive file modes but may still contain child auth material plus bounded stdout/stderr and event summaries for lifecycle recovery and debugging. Treat it as sensitive local runtime state.
- Plugin disposal stops live plugin-managed children and aborts their event readers before registry/notification caches are cleared. Do not rely on child processes surviving a parent plugin reload.

## Configuration

Environment knobs read directly by the plugin:

- `OPENCODE_CHILD_MAX_LIVE`: caps how many plugin-managed children may be live at once. `oc_child_start` rejects new starts past this cap with a "concurrency cap reached" error; stop a child first or raise the per-call `maxConcurrent` arg. Defaults to an internal ceiling when unset.
- `OPENCODE_CHILD_STATE_DIR`: overrides the default child registry location. The default registry lives in a user-private XDG state directory namespaced by project path, not project `.opencode/`. Set this only for explicit fixture/debug use.
- `OPENCODE_BIN`: overrides the `opencode` binary used to spawn children. Safe mode treats it like the `opencodeBin` tool argument and rejects it unless explicitly unsafe-approved.
- `OPENCODE_PLUGIN_DIAGNOSTICS_DIR`: overrides where this plugin (and other opencode plugins sharing the same diagnostics convention) write local diagnostic event logs. Defaults to a project-namespaced state directory when unset.
- `OPENCODE_PLUGIN_DIAGNOSTICS_DISABLED`: set to `1` to turn off local diagnostic event logging entirely.

## Child Notifications

`oc_prompt` registers the prompted child session for best-effort completion notifications back to the parent session. When the watched child session becomes idle, reports an error, appears to be waiting on permission, or the child process exits unexpectedly, the plugin queues a short parent-session continuation with IDs and the relevant `oc_inspect` or `oc_child_status` command.

Notifications are idle-gated: the plugin waits for the parent session to become idle before sending a `promptAsync` continuation, so child completion does not interrupt the active parent turn. `noReply: true` prompts do not notify by default; pass `notify: true` to opt in, or `notify: false` to disable notifications for a prompt.

Important caveats:

- "Idle" does not guarantee success. Inspect the child session for the actual result.
- Notifications are best-effort and tied to the running parent plugin process; V1 does not reattach event tails after parent opencode restart.
- Expected `oc_child_stop` exits are suppressed so manual cleanup does not produce alarming notifications.

## Model Selection

`oc_prompt`, `oc_shell`, and `oc_command` accept an optional model in one of two forms:

- a combined `"provider/model-id"` string, for example `"openai/gpt-5.5"`, or
- separate `providerID` and `modelID` fields, for example `{ "providerID": "openai", "modelID": "gpt-5.5" }`.

`oc_prompt` and `oc_shell` normalize both forms to the nested `{ providerID, modelID }` payload those child endpoints expect. `oc_command` accepts the same public inputs but sends the command endpoint's SDK-shaped plain `"provider/model-id"` string. Bare model IDs without a provider (for example `"gpt-5.5"`) are rejected.

## Skills

This package ships four agent skills under `skills/` for coding agents (such as Claude Code) that read `SKILL.md` files from a project. They are documentation only — opencode does not load them, and they are not part of the published npm tarball.

- `opencode-child-orchestration`: the standard start/inspect/prompt/stop workflow for using this plugin's tools to test another plugin, command, agent, or config change without restarting the parent opencode TUI.
- `opencode-sandbox-safety`: safety defaults (loopback binding, random ports, scratch project dirs, keeping `dangerouslySkipPermissions` off) for evaluating isolation before and during a child run.
- `opencode-permission-triage`: how to read and respond to a child session's pending permission requests via `oc_inspect` and `oc_permission`.
- `opencode-server-api-debugging`: a deterministic checklist (`oc_child_status`, `oc_inspect`, async prompt/shell fallbacks, PID-verified stop) for diagnosing a child server that fails to start, hangs, or won't stop.

## Verification

Public CI runs the deterministic release gate on push and pull request: `npm ci --ignore-scripts --no-audit --no-fund`, `npm test`, and `npm pack --dry-run --json` on Node `20.11.0` and `22.x`.

Run deterministic tests:

```sh
npm test
```

Run a live local smoke test before release. It starts a disposable child server and disposable project by default, so it remains a manual/local gate rather than a pull-request CI job:

```sh
npm run smoke
```

The smoke test does not require model/provider completion. It reports lifecycle, required route compatibility, optional route failures, expected `oc_*` tool registration, a safe-mode negative check, session creation, and PID-verified stop behavior separately. Tool registration uses a separate inherit-mode child because safe mode starts opencode with `--pure`, which disables external plugins. Overall `ok` is true only when lifecycle, required routes, expected tools, and the safety check all pass. If you need to smoke-test a custom binary through `OPENCODE_BIN`, use `OPENCODE_CHILD_TRUST_MODE=inherit npm run smoke`; the default safe-mode smoke path expects `opencode` on `PATH`.
